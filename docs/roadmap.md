# 開発ロードマップ

最初の表は初期 PoC の合格条件。現在は3キー以上と個別の判定オプションを実装済みで、iOra 実機での確認が残っている。[現在の仕様](../README.md)

初期 PoC の合格条件は **コンボが一件もない状態から、任意の二つの物理キー位置を指定して新規作成・編集・削除できること**。たとえば GUI で `J + K → Esc` を新規作成し、そのあと同じファームウェアのまま `U + I → Tab` に変更する。タイムアウトと解放方式は初期段階では固定とする。[選定根拠](features.md) · [推奨設計](architecture.md)

## PoC の段階と合格条件

PoC の初期構成は、USB データ通信、永続 Settings バックエンド、座標付きの単一物理レイアウトを備えた非分割ボードを一台とする。静的な `zmk,combos` を持たない構成で、調査した公式 ZMK リビジョンを使う。ボード名・ホスト OS・ブラウザーは実機の入手状況に合わせて決める。

| 段階 | 作業 | 合格条件 |
| --- | --- | --- |
| 1. west と入力経路 | 外部モジュールを west で導入し、Kconfig で有効化する。リンカーマップと実行トレースで、外部リスナーが Hold-Tap・キーマップより先に位置イベントを受け取ることを確認する。 | 無改変の公式 ZMK でビルドできる。静的コンボの混在を明示的に拒否し、登録ゼロ時は通常入力が通過する。捕捉順や再配信が成立しない場合は案 C に切り替える。 |
| 2. 実機通信と動的作成 | 専用 CDC と簡易 PC ツールで、レイアウト、コンボ一覧、設定の置き換えを扱う。 | 初回の一覧が空で、`.keymap` にコンボ定義を追加せず、任意の二位置で作成できる。同じバイナリで別の位置へ変更すると、旧位置は通常キーとして動く。削除後はどちらの組み合わせも通常入力になる。 |
| 3. 保存と復旧 | Zephyr Settings に定義表を保存し、無効値、保存失敗、途中切断、版またはレイアウト不一致を検証する。 | 再起動・電源抜き差し後も位置と出力が復元される。削除も再起動後に維持される。保存失敗で現行設定が変わらず、保存中の電源断では旧定義か新定義の有効な状態に戻る。 |
| 4. Web と Studio 共存 | Web Serial GUI のキーボード図でキーを選べるようにする。Studio を有効にした同じボードで USB HID と両 CDC の列挙を確認する。 | GUI の空の一覧から作成し、位置の変更・削除・再読込まで行える。Studio のキー・レイヤー編集後もコンボは同じ物理位置で発火し、両アプリからの保存・復元の作用範囲を確認できる。 |

複合 USB が成立しない場合は、endpoint 不足、ボード定義、USB スタック、OS の列挙、RAM のどこで失敗したかを記録する。別の USB 対応ボードで再現性を確認し、単独 PoC と共存対応の判定を分ける。有線の制約が対象機種で継続する場合に、案 B の独自 GATT を再評価する。[公式のモジュール導入](https://zmk.dev/docs/features/modules#building-with-modules) · [公式 Studio の導入条件](https://zmk.dev/docs/features/studio#adding-zmk-studio-support-to-a-keyboard)

## 入力とリソースの検証

- 候補の保留中と成立後の解放待ちに設定を保存し、キーの欠落・二重入力・残留がないことを確認する。時間切れ、順序逆転、二つ目のキーが来ない場合、三つ目の割り込み、候補どうしで一位置を共有する場合、Hold-Tap とレイヤー切替を試す。可能な範囲で同じ条件の標準コンボを比較対象にする。
- 起動直後は通常入力を受け、検証済みの定義があれば適用する。読込フェーズ完了まで書き込みを閉じる。同じ値の再送、応答の消失、不正フレーム、ロック時間切れ、ケーブル切断後の再接続を確認する。
- 標準、モジュールのみ、Studio のみ、両方の4ビルドで RAM、アプリ領域の Flash、Settings 領域、USB interface／endpoint を比較する。スタック使用量、通常入力とコンボの最大遅延、Flash 保存中の入力欠落を記録する。最低限必要な余裕は初回計測値と対象ボードの容量を基に決める。
- 公式の開発用テストで代替できる処理と、物理 USB、Flash 電源断、HID の実機検証を使い分ける。対象リビジョン、ボード、設定、ホスト、測定条件を結果に添える。[ZMK のテストガイド](https://zmk.dev/docs/development/local-toolchain/tests)

## PoC の次に進む条件

| 順序 | 機能・検証 | 着手条件 |
| --- | --- | --- |
| 1 | 分割対応と複数レイアウト | PoC の合格後、split central またはドングルで左右をまたぐ入力、peripheral の切断、再起動を確認する。追加レイアウトは物理位置の変換と欠落位置の扱いを定義してから対応する。 |
| 2 | 短いタップ列を持つ編集可能なマクロ | マクロの需要と用途を確認し、容量と遅延の上限を決める。進行中の設定スナップショットと、キュー満杯でも押下・解放が欠けない実行方法を先に決める。標準キューで一括登録を保証できない場合は、範囲を絞った実行方式か上流 API を比較する。 |
| 3 | 標準コンボとの混在 | 案 C で静的・動的定義を同じ検出器に渡せることを条件とする。 |
| 4 | Hold-Tap、条件付きレイヤー、エンコーダー | ビルド済み Hold-Tap プロファイル切替や回転出力など、機能ごとに運用上の効果と所有範囲を確認する。任意の Hold-Tap プロパティや条件付きレイヤーは、押下状態の継続やレイヤー所有権を扱える拡張点を条件とする。 |

ZMK Studio が対象機能を取り込んだ時点で、編集範囲と移行経路を再確認する。Studio の対応範囲で要件を満たせるなら既存機能を利用する。[Studio の公式機能表](https://zmk.dev/docs/features/studio#capabilities)
