# アーキテクチャ比較と推奨設計

この文書は初期 PoC の設計記録。複数キー、個別判定条件、Behavior 出力、既存コンボの自動取り込みに対応した現在の仕様は [README](../README.md) を参照。現在の実装では初期定義を Devicetree に残し、ZDKM が有効な中央側でのみ ZMK 標準の検出ソースをビルドから外す。

**初期 PoC は案 B。** 公式 ZMK に外部モジュールを追加し、コンボが一件も登録されていない状態から、GUI で任意の物理キー位置と出力を選んで新規作成・編集・削除できることを検証する。通信には専用 USB CDC ACM と Web Serial、キー出力には標準 Behavior、保存には Zephyr Settings を使う。標準コンボと混在し、標準の判定機能まで扱う段階では、検出を一系統にできる案 C を優先する。[技術調査](feasibility.md)

## 方式の比較

工数とリソース消費は相対評価。ボード別の実測値はまだない。

| 評価軸 | 案 A — Studio 基盤を最大限利用 | 案 B — 専用通信と設定管理 | 案 C — 上流に拡張点を追加 |
| --- | --- | --- | --- |
| 実現可能性 | 公式のキー・レイヤー・レイアウト操作は成立。現行の Studio schema にモジュール固有の設定を読み書きする入口はない。 | 標準コンボを構成しない環境で、外部リスナーが限定的なコンボ検出を所有できる見込み。入力イベントの捕捉・再配信を実機で検証する。 | 公式 ZMK にコンボ定義を供給・更新する実行時 API を提案する。採用後の公式版から利用可能。Studio 用 RPC の拡張は独立した選択肢。 |
| 実装の複雑さ | 既存の操作だけなら低。新規 RPC を既存ポートで処理するには schema、生成型、両側の dispatcher／クライアントと互換性の扱いが必要。 | 中〜高。2 キーの組み合わせに絞っても、タイムアウト、再配信、解放、設定の切替が必要。 | 高。公式入力処理とモジュールの境界、更新の一貫性、互換契約を設計する。 |
| 開発工数 | 既存 UI 相当は小。新規設定は現行の前提下で完結せず、上流拡張まで含めると大。 | 中。入力経路を先に実証し、単一構成で通信・保存・GUI を順に検証する。 | 大。仕様合意、回帰テスト、レビュー、採用時期に依存する。 |
| 拡張性 | 既存 schema に従う。汎用拡張が公式に用意された場合は改善する。 | モジュールが所有できる設定型を追加しやすい。公式処理の定義には固有の拡張点が必要。 | 入力処理を一系統に保ちながら、公式が合意した機能に拡張できる。 |
| メンテナンス性 | 既存 RPC の再利用は容易。非公式なタグ、生成物の差し替え、フォークを用いると維持負担が大きい。 | 専用プロトコルと限定された検出器を維持する。入力の相互作用に回帰テストが必要。 | 採用後は上流とテスト・仕様を共有できる。提案・移行中は複数版の対応負担がある。 |
| ZMK 更新追従 | 公式クライアントが扱う既存 RPC は追従しやすい。独自 schema を足す構成では生成型・リンク構成の追従が必要。 | 対応リビジョンを固定し、イベント配送順・再配信、Behavior API、ボードごとの USB を検証する。 | 公式にサポートされる API を採用できれば追従しやすい。採用・安定化時期は未確定。 |
| Studio との共存 | 既存 Studio クライアントは同一デバイスで利用できる。現行 CDC ポートを複数クライアントで同時利用する設計は採れない。 | 別ポートと別設定キーで併用できる見込み。USB endpoint やログとの競合を実測する。 | 共有 transport の場合はセッション、ロック、版の扱いを公式契約に従わせる。機能 API のみ採用された場合は案 B の通信を継続できる。 |
| MCU リソース | 既に Studio 有効なら追加 transport は不要。未使用機種に導入する場合は Studio RPC のスタック、リング、メタデータ等を負担する。 | Studio 無効でも機能する見込み。専用 CDC のほか、定義表、位置別検索、保留イベントとタイマーの RAM を見込む。 | 公式の処理と transport を共有できれば重複を減らせる。動的コンボには可変表・索引や切替状態の追加が必要。 |

案 B の PoC ではコンボ検出を一系統に保つため、静的な `zmk,combos` との混在をビルド時に拒否し、理由を示す。既存コンボの実行優先度を横取りしたり、暗黙に無効化したりすると、入力が変わるため。混在が必要な構成では、案 C で静的・動的定義を同じ検出器に入力する API を検討する。入力の検証を通過できなければ案 C を優先し、PoC の要件は維持する。

## 推奨構成の責務

| 部分 | 責務 |
| --- | --- |
| 独立 Web GUI | キーボード図から二つの物理キーを選び、出力を選択する。空の一覧からの作成、位置と出力の編集、削除、明示的な保存と再読込を提供する。キーに割り当てられた文字は位置の識別子に使わない。 |
| モジュールの通信処理 | モジュール専用 CDC を開き、プロトコル版と機能の確認、受信上限、要求と応答の対応付け、書き込み権限を扱う。Flash 操作は UART コールバックから切り離し、直列の通常スレッド文脈で処理する。 |
| モジュールの設定 | 範囲検証、固定幅のシリアライズ、Zephyr Settings による初期読込・保存、保存済み値の RAM への公開を所有する。 |
| モジュールのコンボ検出 | 位置イベントから候補を照合する。候補位置だけを保留し、成立時は標準 `&kp` へ押下・解放を渡す。不成立時は保留した元イベントを下流へ順番どおりに再配信する。 |
| 公式 ZMK と Zephyr | ZMK のイベント機構、物理レイアウト API、通常キーマップ、Behavior と HID を再利用する。Zephyr が USB クラスと Settings バックエンドを提供する。 |

PoC は単一の物理レイアウトで、実在する任意の異なる二位置、単一のキー出力、全レイヤー共通の固定タイムアウト、最初の解放で出力を解放する規則から始める。ファームウェアには最大件数分の容量を確保し、初期の登録件数はゼロとする。物理キーの位置と座標はモジュールが ZMK の `zmk_physical_layouts_get_list()` と選択中のレイアウトから取得し、GUI に公開する。座標付きレイアウトを PoC ボードの条件とする。[物理レイアウト API](https://github.com/zmkfirmware/zmk/blob/4de3133/app/include/zmk/physical_layouts.h)

候補が成立しない場合に元の押下と解放を欠落・重複させず、元の時刻と順序を保って下流に送る。成立した場合は、コンボが消費したキーの解放を最後まで追跡する。入力処理とタイマーの状態変更は直列化する。設定の適用は保留中の候補や成立済みコンボの解放待ちが解消した境界で行う。通常キー、Hold-Tap、レイヤー操作に生じる影響を先に検証する。[イベント機構](https://zmk.dev/docs/development/events)

## 通信の選択

| 候補 | 判断 |
| --- | --- |
| USB CDC ACM + Web Serial | **PoC の第一候補**。Zephyr の既存 CDC ACM と UART API を利用でき、有線で列挙から復旧まで追いやすい。専用 CDC ノードを使い、Studio やログとは別ポートを選ぶ。対応するデスクトップブラウザーで、HTTPS またはセキュアな localhost と利用者によるポート選択が必要。[Chrome Web Serial](https://developer.chrome.com/docs/capabilities/serial) · [Zephyr Legacy CDC ACM](https://docs.zephyrproject.org/latest/samples/subsys/usb/legacy/cdc_acm/README.html) |
| 独自 BLE GATT + Web Bluetooth | USB ポート不足または無線要件が判明した場合の候補。独自 UUID、暗号化された接続、発見方法、ペアリング・ボンド、MTU と分割、HID および split リンクとの共存を検証する。Studio GUI の Linux 限定フィルターは Studio の選択条件であり、本プロジェクトの対応 OS は別途検証する。[Chrome Web Bluetooth](https://developer.chrome.com/docs/capabilities/bluetooth) · [ZMK の BLE 広告処理](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/ble.c) |
| USB ベンダー定義 HID + WebHID | 別のレポート経路を設計すれば候補。通常のキーボード HID はブラウザーの保護対象であり、ZMK の HID レポート登録をそのまま設定通信に使う構成は採用できない。レポート記述子、USB endpoint、ブラウザー許可に追加検証が要る。[Chrome WebHID](https://developer.chrome.com/docs/capabilities/hid) · [ZMK USB HID](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/usb_hid.c) |

PoC の通信は上限付きの改行区切り要求／応答とし、機器・版・レイアウトの照会、コンボ一覧の取得、一覧の置き換えを用意する。作成・編集・削除は小さな定義表の更新として扱う。デバイス側で件数、実在する位置、同一位置の重複、同一組み合わせ、出力値、レイアウト識別子を検証する。一度に一要求を処理し、入力不正、ロック中、領域不足、保存済みで適用待ちなどを区別する。書き込みはキーボード上の明示操作で短時間だけ許可し、起動・切断・時間切れで閉じる。

## 保存・共存・更新の方針

- 名前空間は例として `zdkm` を使う。レコードには形式の版、物理キー位置の対応を識別する情報、位置の組と出力の一覧を保存する。保存値が存在しない場合は空の一覧で起動する。破損、未知の版、互換性のないレイアウトは元のキー入力を維持し、状態を通知して明示的なリセットまで自動上書きを避ける。
- 検証済みの定義表を一件の Settings レコードとして保存し、成功後に入力処理の安全な境界で RAM の定義を切り替える。それまで GUI は「保存済み・適用待ち」と表示し、保留中は次の更新を受け付けない。保存失敗時は現在の定義を保つ。同じ内容の再送では書き込みを省略する。応答を失った場合は再接続して保存済み・適用済みの状態を読む。Flash 書き込みは入力の排他区間から外す。
- Studio のキーマップ保存とモジュール設定の保存は別操作とする。PoC では Studio の Restore Stock Settings にモジュールのリセットを登録しない。モジュール側の既定値復旧手順を用意する。共有 Settings パーティション全消去時には両方の保存値が失われる。[Studio の復元処理](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/studio/core_subsystem.c) · [ZMK の NVS 全消去処理](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/settings/reset_settings_nvs.c)
- 対応する ZMK リビジョンを west manifest で固定し、Zephyr の版は ZMK の manifest に従う。更新時は依存ヘッダー、USB 列挙、Settings の復旧、入力経路、Studio 共存を検証してから対応を宣言する。設定型が増えるまでは単一レコードと単一 transport の構成を維持する。

ボード、対応ブラウザー、設定の上限などは PoC の検証条件であり、製品の固定仕様は実測後に決定する。[開発計画](roadmap.md)
