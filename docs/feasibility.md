# 技術的な実現可能性と制約

調査対象は [機能一覧のリビジョン](features.md) に固定した。以下の「確認」は公式ソースか公式文書による静的な確認、「設計評価」はそこから導いた実装可能性の判断。ビルド、リンク、実機、ブラウザーおよび電源断試験は今回の調査に含まれない。

## Studio の通信と拡張境界

| 確認したこと | ファイル・シンボル |
| --- | --- |
| RPC は Protobuf を nanopb で処理する。開始・終端・エスケープを持つフレームを使い、要求 ID 付きの応答と非同期通知を区別する。受信リングからデコードし、subsystem と operation のタグでハンドラを選択する。 | `proto/zmk/studio.proto` の `Request`、`Response`、`Notification`。 `app/src/studio/rpc.c` の `rpc_main()`、`handle_request()`、`zmk_rpc_subsystem_delegate_to_subs()`。[公式プロトコル](https://zmk.dev/docs/development/studio-rpc-protocol) · [公式 schema](https://github.com/zmkfirmware/zmk-studio-messages/blob/6cb4c28/proto/zmk/studio.proto) · [RPC 実装](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/studio/rpc.c) · [フレーミング](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/studio/msg_framing.c) |

**設計評価**。既存 Studio クライアントと通信コードは、定義済みの公式 RPC に対して利用できる。モジュール固有の読み書きに同じ CDC ポート、GATT characteristic、または Studio の keymap 保存コマンドを流用するには、公式 schema／dispatcher 側の拡張が必要になる。リセットの登録点は存在するため、将来両アプリから初期化する要件が出た場合に利用を評価できる。

## 任意の発火位置を持つコンボの成立条件

- **確認**。標準コンボのリスナーは `app/src/combo.c` の `DT_HAS_COMPAT_STATUS_OKAY(zmk_combos)` による条件コンパイル内にある。成立前の押下イベントを保存し、`release_pressed_keys()` が `ZMK_EVENT_RELEASE` または再 raise を使って処理を継続する。イベントマネージャーの `zmk_event_manager_release()` は捕捉したリスナーの次から配送する。[標準コンボ実装](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/combo.c) · [イベント実装](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/event_manager.c)
- **設計評価**。標準コンボを有効にしない構成なら、先に配送される外部リスナーで任意の二位置を検出し、成功時は `zmk_behavior_invoke_binding()` で `&kp` を呼べる見込み。Hold-Tap より前の捕捉順、候補に失敗した場合の元イベントの再配信、遅延後のタイムスタンプ、キー解放をビルドと実機で検証する。標準コンボと同じ入力を奪い合う構成は初期の対象から外す。[公式イベントガイド](https://zmk.dev/docs/development/events) · [Behavior 呼び出し](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/behavior.c)
- **比較事例**。nemu-link 向けの公開モジュールにも、任意位置を指定する実行時コンボがある。公開 README では ZMK のコンボリスナーを再利用し、静的コンボとの混在をビルド時に拒否する。対応する ZMK フォークを前提とするため、公式 ZMK 無改変の案が実機で成立した証拠には含めていない。[nemu-link Dynamic Combo](https://github.com/sekigon-gonnoc/zmk-feature-dynamic-combo)

## 永続化と復旧


- **確認**。ZMK の `app/src/main.c` は `CONFIG_SETTINGS` 有効時に `settings_subsys_init()` と `settings_load()` を呼ぶ。Studio の `save_changes()` は物理レイアウト選択を保存し、その後 `zmk_keymap_save_changes()` が変更バインディング、順序、名前を個別に保存する。 `discard_changes()` は初期値と保存値に戻す経路を持つ。複数キーの保存は段階実行で、全体で一つの Flash トランザクションを構成していない。[起動コード](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/main.c) · [Studio 保存・破棄](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/studio/keymap_subsystem.c) · [キーマップ保存](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/keymap.c)
- **確認**。Zephyr Settings は `SETTINGS_STATIC_HANDLER_DEFINE`、`h_set`／`h_commit`、`settings_save_one()`、`settings_delete()` を提供する。実際の媒体や制約はビルドで選ばれるバックエンドに依存する。NVS では領域とセクター消去が制約になり、ZMK の NVS 向け全消去 `zmk_settings_erase()` は共有パーティションを消す。[Zephyr Settings](https://docs.zephyrproject.org/latest/services/storage/settings/index.html) · [Zephyr NVS](https://docs.zephyrproject.org/latest/services/storage/nvs/nvs.html) · [ZMK の NVS 全消去処理](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/settings/reset_settings_nvs.c)
- **確認**。ZMK の `main()` は Settings の初期化・読込結果を受け取らず、固定版 Zephyr の `subsys/settings/src/settings_store.c` にある `settings_load_subtree()` は各バックエンドの読込結果を集約せずに commit へ進む。したがって `h_commit` は読込フェーズ終了の目安にはなるが、媒体全体の正常性の証明には使えない。`settings_save_one()` は保存先未登録時およびバックエンドの保存時にエラーを返す。[ZMK の `main()`](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/main.c) · [依存版 Zephyr の Settings 実装](https://raw.githubusercontent.com/zmkfirmware/zephyr/v4.1.0%2Bzmk-fixes/subsys/settings/src/settings_store.c)
- **設計評価**。モジュールは専用の名前空間と、固定幅で版を持つ小さなレコードを使用できる。保存に成功してから RAM の設定を切り替えると、保存失敗時に現在の動作を保てる。設定一件にして部分更新の範囲を狭めても、電源断からの復旧は対象バックエンドで確認が必要。読み込み完了前の書き込みは受け付けず、未登録と読込障害を区別できるかをビルドで検証する。Flash にポインター、C 構造体の生バイト、配列上の一時 ID を保存する必要はない。

## リソースと機種制約

| 項目 | 確認事項と測定方針 |
| --- | --- |
| RAM／Flash | 調査対象の Studio Kconfig 既定値は RPC スタック 4096 B、RX/TX 30/64 B、割り込みなし UART を選んだ場合の RX スタック 512 B。公式 Configuration ページの RPC スタック表は 1800 B と差があるため、ボードごとの `zephyr/.config` とリンク結果を採用する。外部モジュールの増分は CDC のバッファ・処理スタック、設定の現在値・押下時の値、処理コード、USB descriptor 等。Studio なし／あり双方で `ram_report`、`rom_report` と map を比較する。設定領域自体の空きとアプリ用 Flash 容量も別に確認する。[Studio Kconfig](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/studio/Kconfig) · [公式 Studio 設定](https://zmk.dev/docs/config/studio) |
| コンボの規模と入力負荷 | 公式コンボの位置別索引だけで、ソース上は `4 × ZMK_KEYMAP_LEN × ceil(コンボ子ノード数 / 32)` B。候補マスク、最大コンボ長に比例する捕捉・アクティブ状態、定数表は別途必要。動的コンボの PoC は設定表、候補の検索、保留イベント、解放待ちとタイマーの RAM を追加する。登録ゼロ・対象外のキーは遅延なしで後続に流し、候補位置の通常入力はタイムアウトまで遅れうる。通常入力の遅延、コンボ発火時、連続入力中の Flash 保存でイベント欠落と最大遅延を比較する。[コンボ配列](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/combo.c) |
| USB | PoC の CDC ACM には USB デバイス対応のボード、データ接続、対象 USB スタック、CDC 用 endpoint が要る。Studio や USB ログとの複合構成は endpoint と RAM の余裕を実機で検証する。Studio のガイドも STM32F072 等の RAM 制約を挙げている。USB を持たない構成には別 transport が必要。[Studio 導入条件](https://zmk.dev/docs/features/studio#adding-zmk-studio-support-to-a-keyboard) · [Zephyr Legacy CDC ACM](https://docs.zephyrproject.org/latest/samples/subsys/usb/legacy/cdc_acm/README.html) |
| 分割・左右・ドングル | central がキー位置イベントからキーマップを評価し、peripheral は入力を転送する。コンボは central 側からローカル source の仮想位置で出力を呼ぶ。動的コンボの定義と検出器を central に置く設計が可能。左右をまたぐ入力、peripheral の切断／再接続と USB 可否は実機で確認する。選択レイアウトが変わるとコンボ位置を期待どおりに再対応づけられない事例が報告されており、初期検証は単一レイアウトとする。[公式 split ガイド](https://zmk.dev/docs/features/split-keyboards) · [central の入力経路](https://github.com/zmkfirmware/zmk/blob/4de3133/app/src/split/central.c) · [ZMK Issue #3228](https://github.com/zmkfirmware/zmk/issues/3228) |

標準コンボを構成しない PoC では、公式のイベント機構を利用し、外部モジュールが二位置コンボの検出を所有する案を先に検証する。標準コンボとの混在や高度な判定は、ZMK の検出器を共有できる上流の実行時 API を優先する。[比較と設計](architecture.md)
